# 架构说明 —— 从全栈单服务改造为纯静态站

> 上一版是 Next.js 16 + Prisma 7 + SQLite 的单进程单端口服务。
> 这一版把它改造成**纯静态前端**，为的是能免费发布到 GitHub Pages。
> 这篇写清楚：改了什么、为什么这么改、以及怎么改回去。

---

## 1. 改造前后

| | 改造前 | 改造后 |
| --- | --- | --- |
| 运行方式 | Node 进程，监听 3000 端口 | 一堆静态文件，没有进程 |
| 框架 | Next.js 16 App Router（服务端渲染 + Server Actions） | Vite 7 + React 19（客户端渲染） |
| 路由 | 文件系统路由 | react-router 7 + `404.html` 回落 |
| 数据库 | SQLite 文件 + Prisma 7 | 浏览器 IndexedDB |
| 查询 | `src/server/*` 里的 Prisma 查询（async） | `src/data/queries.ts` 里的纯函数（sync） |
| 写操作 | Server Actions | `src/data/mutations.ts` |
| 登录 | 排期中（Cookie Session + argon2） | Google 登录 / 本地账密（PBKDF2） |
| Excel 导出 | 服务端 `/api/export/[kind]` | 浏览器里生成 Blob 下载 |
| 托管成本 | 一台机器 | 0 |

**没变的**：数据模型的字段与语义、视图模型的返回结构、业务判定规则
（停滞 7 天、利润率预警 11%、中信保 85%）、金额用整数分存的约定、
写操作必须留痕的约定。

## 2. 为什么数据放 IndexedDB，而且整库存一条记录

先说为什么不是 localStorage：它是同步 API，写 300 KB 台账会卡住主线程；
5 MB 的上限对导入过 Excel 的账套也不够用。

再说为什么不按表分 object store，而是把整个 `Database` 对象存成一条记录：

这个数据量是**千行级**，一次性读进内存完全撑得住。换来的好处很实在：

1. **查询是同步的。** 表格筛选、排序、看板聚合都不用 `async`，
   页面里没有一处 loading 状态需要传递。`useSyncExternalStore` 订阅内存库，
   任何一次写入自动重渲染所有订阅者 —— 没有一行 refetch 代码。
2. **写入天然是原子的。** 一次 `put` 要么整库更新要么不动，
   不会出现「批次更新了但动态流水没写进去」这种半截状态。
3. **导出就是 `JSON.stringify`。** 备份、迁移、发给同事复现问题，都是一个文件。

代价是每次写入要把整个对象序列化一遍。实测千行级在几毫秒量级，
而且写入本来就防抖了 220ms，一次批量更新只落一次盘。

```
组件  ──useDb()──▶  useSyncExternalStore
                          │
                    src/data/db.ts   ← 内存里的 Database（唯一真相）
                          │  mutate()
                          ▼
                    防抖 220ms → IndexedDB（一条记录）
```

## 3. 演示数据的时间轴跟着「今天」走

原始台账是照 2026-08-07 那天的真实业务写的。如果把日期写死，
这个演示站放上半年后会变成一堆「全部超期」的死数据 ——
停滞、超期、本月出运这些判定全部失效，看板首屏一片红。

所以 `src/data/seed.ts` 里所有日期都按 `today − ANCHOR` 的差值整体平移。
生成的批次还会**反着推时间轴**：先决定这票走到第几步，
再把「下一个待办节点」摆到今天前后（约 14% 落在过去 → 超期）。
不这么做的话，随机出来的批次绝大多数都会显示成超期。

手写的那批行（客户备注、动态、产品名）一个字都没改 ——
生成器写不出「并柜方还差一家没进仓，货代说最晚 8 号截仓」这种话。
机器只负责在它们周围补量，主线剧情还是手写的。

## 4. 认证：能做到什么，做不到什么

**做不到的**：真正的认证。没有服务端就没有服务端校验，
浏览器里跑的校验逻辑，改改前端代码就能绕过。

**做到的**：

- **Google 登录**走官方 Google Identity Services，拿到的 `credential` 是一个真实的
  JWT。前端只解 payload 用于**认人**（头像、名字、邮箱），不用于**授权**。
  要接真后端时，把这个 credential 原样 POST 给服务端验签即可，
  `src/auth/google.ts` 一行不用改。
- **账密登录**用 WebCrypto 的 PBKDF2-SHA256、随机盐、12 万轮，跟真后端一个做法。
  它解决的是「别让口令以明文躺在别人的电脑上」—— 共用机器、浏览器同步、
  导出的账套 JSON 都可能被看到。导出账套时凭据会被整段剔掉。
- **角色与数据范围**是真的在生效：角色（`admin` / `sales` / `finance` / `viewer` …）
  决定能不能写，数据范围（`self` / `team` / `all`）决定 `listShipments` /
  `listOrders` / `listCustomers` 返回哪些行。用 `viewer` 登录，所有写按钮都是禁用的。

这三件事在演示站上是**产品能力的展示**，不是安全边界。数据本来就都在
用户自己的浏览器里，越权也越不到别人的数据。

## 5. 部署：两条 base 路径

GitHub Pages 有两种站点，路径不一样：

| 站点 | URL | base |
| --- | --- | --- |
| 用户站点 | `https://decli.github.io/` | `/` |
| 项目站点 | `https://decli.github.io/ForeignTradeManagementSystem/` | `/ForeignTradeManagementSystem/` |

资源路径和路由 `basename` 都得跟着 base 走，所以构建两次：

```bash
npm run build:root       # base = /
npm run build:project    # base = /ForeignTradeManagementSystem/
```

运行时 `src/main.tsx` 从 `import.meta.env.BASE_URL` 取 basename，两种部署共用一套代码。

**深链接 404**：Pages 是纯文件服务，请求 `/follow-ups` 时磁盘上没有这个文件。
构建插件把 `index.html` 再拷一份成 `404.html`，Pages 找不到路径时会把它吐回来，
浏览器照常执行 SPA，路由读 `location.pathname` 渲染出正确页面。
URL 保持干净，不用 hash 路由。

## 6. 接回真后端

需要动的只有一个文件：`src/data/db.ts`。

它现在对外只暴露四件事：

```ts
load()                       // 装载账套
snapshot()                   // 取当前账套（同步）
mutate(draft => { ... })     // 唯一写入口
subscribe(fn)                // 变更订阅
```

接后端有两条路：

**A. 保持同步查询（推荐，改动最小）** —— `load()` 改成一次 `GET /api/snapshot`
把账套拉下来，`mutate()` 改成「本地先改（乐观更新）+ `POST /api/mutations` 上报，
失败则回滚」。`queries.ts`、所有页面组件、DataGrid 全部不用动。
适合单公司、数据量在万行以内的场景 —— 也就是这个系统的实际场景。

**B. 改成按需查询** —— `queries.ts` 里的每个函数换成一次 fetch，
返回结构保持现在的字段名不变，页面组件把 `useMemo` 换成数据获取 hook。
工作量集中在页面的加载态，视图模型和样式不用动。

数据模型这边，`src/data/types.ts` 是原 Prisma schema 的平移，字段名一一对应，
把它翻回 `schema.prisma` 是机械劳动。两条硬约定（金额整数分、
状态存字符串不用枚举类型）就是为了这一步留的。

## 7. 采购与资金侧的数据模型

主模型（`types.ts`）覆盖的是「货」这条线：PI → 出运 → 退税。
`ops-types.ts` 补上「货怎么来」和「钱怎么走」：

```
询价单 ──比价──▶ 采购合同 ──下单──▶ 生产单 ──交货──▶ 出运批次
   │                  │                                  │
   └── 供应商 ────────┘                                  │
                      付款计划 ◀── 收付款 ──▶ 应收 ◀──────┘

库存 ──锁库──▶ PI          运费航线 ──中标价──▶ 订单成本
单证 ──挂靠──▶ 出运批次     登录记录 ──▶ 账号
```

它单独一个文件、单独一份种子（`ops-seed.ts`），但**所有记录都挂回已有的 PI**。
不挂的话这些模块就是几张互不相干的空表，演示不出「一条 PI 号串起全流程」这件事，
而这恰恰是外贸系统的核心价值。

### 种子数据的内部一致性

演示数据最容易出的问题不是「不好看」，是**互相对不上**。几个真实踩过的坑：

| 症状 | 根因 |
| --- | --- |
| 资金汇总显示净流出是收汇的 6 倍 | 采购合同金额是随机数，跟它挂的 PI 无关，出现「卖 5 万美金的单子签了 700 万人民币采购合同」。改成按售价的 62%~82% 推，数量再从金额反算 |
| 费用明细报表算出 775% 的费用率 | 期间费用四项原本占售价 65%（42/12/8/3）。订单页看堆叠条看不出问题（没人拿它跟应收比），一到汇总口径就露馅。改成合计约 8% |
| 科目表出现负毛利 | 收入口径取的是「应收」，而有一批订单还没到开票节点 `ar = 0`、成本却已发生。收入应该取 PI 金额，应收是另一件事 |
| 「库龄超 120 天 = 0」而「半年内到期 = 全部」 | `daysBetween(a, b)` 算的是 `a − b`，两处参数都写反了 |
| 开票资料把 8 家供应商全判成不合格 | 统一社会信用代码是 18 位，种子里写成了 17 位 |

结论：**任何一个跨模块的汇总页，都是对种子数据的一次积分测试。**
单页看每个数都对，加起来才知道口径有没有错。

## 8. 中英切换

`src/i18n/` 三个文件，没有引任何 i18n 库。

**用中文原文当 key**，而不是 `page.followups.title` 这种符号。理由见 README，
这里只说工程上的两个决定：

**1. 组件内用 `t()`，组件外用 `tr()`。**
`t()` 来自 `useT()`，订阅语言变化。但有些显示文案不在组件里 ——
看板的风险清单在 `queries.ts` 生成，跟单抽屉的齐套检查表在一个普通函数里。
它们用模块级的 `tr()`，读一个由 `LangProvider` 每次渲染同步的模块变量。
调用方（组件）在语言变化时重渲染，会带着它们一起重算，所以不会滞后。

**2. 模块级常量表保持中文。**
`ENTITY_LABEL`、`PRODUCTION_STATUS` 这类映射表在模块作用域，调不了 hook。
它们的值**本身就是词条 key**，翻译发生在渲染处：`t(PRODUCTION_STATUS[x])`。

### 一个必须绕开的坑

批量把中文包进 `t()` 时，**绝对不能碰拿中文当数据比较的地方**：

```ts
s.releaseState === "已放行"     // 包了 → 中文界面照常，英文界面永远为 false
r.action.includes("删除")
RELEASE_TONE["未放行"]
```

这类 bug 只在切到英文时出现，而且不报错、不崩溃，只是逻辑静默失效 —— 最难查。
所以 codemod 只在**明确是展示位**的地方动手（对象里的展示字段、JSX 展示属性、
JSX 文本节点），并对 `===`、`.includes(`、`[` 等前缀做前瞻拦截。

## 9. 受控输入框与中文输入法

站内的搜索框曾经**只能打英文**：敲拼音，候选框刚冒出来就没了，一个汉字也上不去。
偏偏右上角 ⌘K 那个搜索框好好的。

### 不是输入法的问题，是「这个框的值存在哪」的问题

出问题的框，值都存在地址栏参数里（`useParam`）。react-router v7 的
`setSearchParams` 是包在 `startTransition` 里的 —— 这次更新被降级成可打断的，
**本轮事件循环里不提交**。而 React 在事件派发收尾时会做一次
`restoreControlledState`：发现 DOM 里的值跟上一次渲染的值对不上，就把 DOM 的
`value` **写回旧值**；等下一帧 transition 提交了，值再变回来。

拿浏览器实测，敲一个 `n` 的瞬间：

```
同步读 input.value → ""     ← 被写回去了
一帧之后再读       → "n"
```

打英文时这一来一回你看不见，所以从来没人发现。但对输入法来说，**程序去写
`input.value` 就等同于宣布「合成结束」** —— 拼音缓冲清空，候选框关闭。
⌘K 那个框用的是 `useState`，紧急更新，同步就提交了，DOM 和渲染值始终一致。

### 修法：打字期间这个框自己说了算

`useTextField`（`src/lib/hooks.ts`）在本地留一份镜像，渲染用镜像：

- 每次按键都是一次**紧急** `setState`，React 提交完再去比对，值是对的，不回写 DOM；
- 外面传进来的值只在「不在合成中」且「确实是别人改的」时才采纳 ——
  清空按钮、浏览器后退、从别处带参数进来走的都是这条路；
- 合成期间不往外传半截拼音：搜「ni」没有意义，还会让整张表白闪一下。

这个修法对**上游怎么更新**是不敏感的：不管调用方是同步 `setState`、
transition，还是一个 `await` 之后才回填的异步写库，输入框都不会被打断。

> 验证方式：一段探针脚本走遍 28 条路由，对每个文本框派发一次真实的
> `compositionstart → input(isComposing) → compositionend` 序列，
> 检查 input 事件**同步返回后**的 `value` 有没有被改写。
> 24 个文本框，修完全绿。这个脚本值得在改动输入相关代码后重跑。

## 10. 售前漏斗与报价核算

系统原来从 PI 开始，而业务员八成的时间花在 PI **之前**。补上的这一段是：

```
询盘 ──分配/SLA──▶ 报价（多版本议价）──转──▶ PI
  │                      │
  └── 寄样 ──催反馈───────┘
```

### 三条硬约定

**1. 报价明细行与 PI 明细行同构。** `QuoteLine` 和 `PiLine` 字段一一对应，
转 PI 时整行搬过去，不做任何「翻译」。一旦要翻译，就一定有字段在翻译中丢掉 ——
通常是 HS 编码和包装参数，而那正是三个月后做装箱单和报关时要用的东西。

**2. 单价用 E4（4 位小数），不用「分」。** 口罩成交价是 $0.0850 一只，
手套 $0.0285。整数分只能存成 8 或 9 分，一张 72 万只的单据会差出四千多美元。
金额仍然是整数分，汇率是 E6 —— 三个精度各司其职。

**3. PI 金额是明细行合计的缓存，不是另一个真相。** 改明细行会同步重算
`Pi.amountCents`（见 `mutations.ts` 的 `resyncPiAmount`）。允许两边分头维护，
迟早会出现「发票上写 19,224，系统里显示 19,180」。

### ⚠️ 退税公式：整个核算里最容易算错的一处

常见的错法是「退税 = 采购额 × 退税率」。实际税则是：

```
退税额 = 含税采购额 ÷ (1 + 征税率) × 退税率
```

征税率 13%、退税率 13% 时，实际退回的是采购额的 **11.50%**，不是 13%。
一单 100 万人民币的采购，两种算法差 1.5 万 —— 报价上差 1.5 个点，
足以把一单本来能赚的生意报成亏的。见 `lib/quote-calc.ts` 的 `lineRefundCents`。

### ⚠️ 保费的循环依赖

CIF 按货值的 110% 投保，而「货值」就是 CIF 报价本身 —— 保费依赖报价，
报价又要含保费。反算时用闭式解拆开：

```
R = (固定成本 − 退税) / (1 − 银行费率 − 1.1×保险费率 − 目标利润率)
```

不用迭代逼近：迭代在利润率接近 100% 时不收敛，而用户真的会手滑输 99%。
分母 ≤ 0 时返回 0，界面显示「这个目标做不到」而不是一个荒谬的天价。

### ⚠️ 贸易术语后面跟哪个地名

Incoterms 里这个地名随术语而变：EXW / FOB / FCA 跟**装运港**，
CFR / CIF / DDP 跟**目的港**。写反了就是一张自相矛盾的单据 ——
「FOB Brazil」（巴西没有我们的船），客户的清关行会打电话回来问。
见 `lib/docs.ts` 的 `termPlace()`。

## 11. 出口单据

三张：形式发票 / 商业发票 / 装箱单，都从同一批 `PiLine` 生成。

**为什么走浏览器打印而不是生成 PDF 文件。** 生成 PDF 要么引一个几百 KB 的库
（这个项目零依赖），要么在服务端做（没有服务端）。浏览器的「打印 → 存储为 PDF」
本来就是一等公民路径：排版由 CSS 控制，中文字体不用嵌、不会乱码。
打印样式用 `visibility: hidden` 而不是 `display: none` 隐藏应用外壳 ——
后者会让浏览器丢掉分页计算，长单据第二页开始表头不再重复。

**⚠️ 单据语言跟界面语言是两件事。** 这些纸最终落在客户的采购、他们的清关行、
他们的银行手里，那里没人读中文。所以单据默认英文，界面切成中文**不会**改变
发出去的单据；另有一档「中英对照」给内部复核用。国名、计量单位（件/只/台）
也都有英译表（`lib/geo.ts` 的 `EN_BY_COUNTRY`、`lib/docs.ts` 的 `UNIT_EN`），
一张写着「COUNTRY: 巴西 / QTY: 3,200 台」的发票等于废纸。

金额大写（`SAY US DOLLARS ... ONLY.`）是清关和银行审单要看的，缺了有些国家会退单。

## 12. 附件与本地备份

### ⚠️ 上线时踩的一个真事故：不要升级已经装着用户数据的库

第一版把附件和备份两个 store 加进 `mt-tradeflow`，版本从 1 升到 2。
本地开发一切正常（本地库本来就是新建的），一上线**所有老用户打开就卡在
「正在装载账套…」永远转下去** —— 升级请求被一条挂在后台（bfcache 里的老页面）
的 v1 连接挡住，而那种情况下连 `onblocked` 都不触发，请求就那么静静地悬着。

加超时兜底能让页面至少打开，但代价是退成纯内存模式：用户的数据不再落盘。
所以那不是解法，只是止血。

**真正的解法是不要制造阻塞**：主账套库 `mt-tradeflow` 版本永远停在 1，
一个字节都不动；附件本体和备份快照放进一个新库 `mt-tradeflow-aux`，
它以 version 1 打开，跟老库的连接毫无关系。

> 一个已经装着用户全部身家的库，每一次版本变更都是一次可能把人锁在门外的赌博。
> 能加新库就别升老库。

超时 / `onblocked` / `onversionchange` 三层保护仍然保留，将来真要升版本时用得上。

**附件本体不进 `Database` 那条记录。** 元信息（谁传的、多大、什么单据）跟着账套走，
文件本体进 IndexedDB 的 `files` store，只留一个键。理由是写入代价完全不同：
主库每改一个字段都要整条重新序列化落盘，一份 8MB 的提单扫描件混进去，
以后每次改备注都要顺带重写这 8MB。

**备份按天保留 7 份，不按次。** 每次写入都存一份的话配额几分钟就满，
而且十份都是同一分钟的数据，回滚时根本挑不出想要的那份。
用户想回到的通常是「昨天那个样子」。回滚前会先把**当前状态**也备一份 ——
点回滚的人往往是慌的，回错了还得能回来。

它挡得住误删、导错、改崩一张表；挡不住换电脑、清空站点数据、硬盘坏。
设置页里那句「定期导出 JSON 存到网盘」不是免责声明，是操作建议。

## 13. 协同：做到了什么，没做到什么

纯静态托管没有服务端，所以做不到「多台电脑看同一份数据」。
但协同的机制不止网络那一段，它是三件事：

1. 别人改了，我这边要知道；
2. 要能无缝把变更接过来，而不是弹一句「数据已过期请刷新」；
3. 两边同时改同一条时，要有说得清的裁决规则。

这三件事在同一台机器的**多个标签页**之间完全成立，而且实现一模一样。
所以 `data/sync.ts` 用 `BroadcastChannel` 把它真的跑起来了 ——
开两个标签页，一边改，另一边立刻变（实测：A 页改自定汇率 6.5432，
B 页顶栏同帧更新，无刷新）。

裁决规则是**最后写入者胜**：整库是一条记录，广播的就是整份快照，收到就整份换上。
同一个人开几个标签页够用；真到多人并发要换成 op 级合并 —— `SyncOp` 接口已经定好。

接后端时实现一个 `SyncAdapter` 塞给 `setAdapter()` 即可，`localTabAdapter`
就是照着这个接口写的参考实现，上层一行不用动。

⚠️ 两个坑：
- `adoptRemote()` 接快照时不能走 `mutate()` —— `mutate` 会广播，广播回去就是无限来回。
  用一个 `adopting` 标志把回环掐掉。
- `load()` 读到持久化账套时仍然要过一遍 `hydrate()`。看起来多余，实际救过一次：
  开发中途版本号已经升到新值、而新表还没写进 seed，那一刻存下的账套就是
  「版本对、表缺」的，读回来直接白屏。**版本号只能证明结构世代，证明不了每张表都在。**

## 14. ⚠️ 日期差值的方向

`daysBetween(a, b)` 算的是 `a − b`，这个方向从名字上看不出来。
写的时候要在脑子里推一遍「到期日减今天是正还是负」，而一屏代码里推十次
总有一次推反 —— 曾经一次性写反了五处：报价全部显示「已过期」、
样品全部「还没到期」、账龄全是负数。每个数字看着都合理，只是意思反了。

现在有两个语义明确的包装，新代码一律用它们：

```ts
daysUntil("2026-09-01")   // 还有几天（未来为正）
daysSince("2026-07-01")   // 过了几天（过去为正）
```

## 15. 字段级权限

行级权限（`scope`：self / team / all）解决的是「能看到**哪几行**」。
外贸公司最常提的另一条要求是另一个维度：

> 同一张订单，业务员看得见售价，看不见我从工厂拿的底价。

这是行级权限做不到的 —— 那张单子他必须看得见，否则活没法干。
要挡的是**同一行里的某几列**。见 `lib/perms.ts`。

⚠️ **它挡不住技术手段。** 数据在浏览器里，懂技术的人翻 IndexedDB 就能看到。
这一点必须说清楚，不能让老板以为这是加密。它挡的是「同事凑过来看一眼屏幕」和
「业务员顺手导出一份成本表带走」——而这两件事恰恰是老板真正担心的。
接了后端之后，同一个判断挪到服务端，敏感字段根本不下发，那时才是真的挡住。

被挡住的值显示 `••••` 而不是 `—`：破折号会被读成「这个单子没有成本」，
而实际是「有，但不给你看」。核对账目时这两件事天差地别。

## 16. 明确不做的事


- **不引 UI 组件库**。这是一个数据密度极高的台账应用，
  冻结列、列宽拖拽、密度切换、卡片降级这些都要贴着业务改，
  组件库的默认样式会被覆盖到面目全非，还留下一份删不掉的依赖。
- **不引图表库**。只需要三种图，任何主流库的体积都超过整个应用的其余部分，
  而且默认配色会跟设计令牌打架，深色模式还要再改一遍。手写 SVG 反而更省事。
- **不引状态管理库**。唯一的全局状态是账套，`useSyncExternalStore` 直接够用；
  筛选条件写在 URL 里，本来就不该进内存状态。
- **不做 PWA / 离线缓存**。整站已经是静态文件，浏览器缓存就是离线能力；
  再叠一层 Service Worker 只会让「用户看到的是不是最新版本」变复杂。
- **不引 i18n 库**。只有中英两种语言、一层扁平词条、没有复数规则和日期本地化的
  复杂需求（日期一律 ISO，金额按币种符号）。i18next 那一套的体积和心智负担
  换不来任何东西 —— 见第 8 节，全部实现不到 100 行。
- **不引动画库**。所有动效都是 CSS transition + 两三个 `@keyframes`，
  唯一需要 JS 的是「光晕跟随鼠标」，那也只是往元素上写四个 CSS 变量。

## 17. ⚠️ 账套迁移：版本号变更是一次赌博

`load()` 原来的规则是「`saved.version !== DB_VERSION` 就 `buildSeed()`」，
注释写得很坦白：*演示站没有迁移脚本这回事*。

演示站上这是对的。可一旦有人把真单据录进来，它就是**静默的数据销毁**：
升一次版本，一年台账被 63 张演示 PI 盖掉，全程没有一句提示。
而后面每一件事（附件、分批明细、收款计划）都要加表 —— 也就是说，
不先修这一条，每加一个功能就毁一次用户数据。

现在的规则只有一条：**存过的账套永远保留。**

| 情况 | 处理 |
|---|---|
| 缺整张表 | `hydrate()` 补空数组 |
| 缺字段 | 迁移阶梯补默认值 |
| `saved.version > DB_VERSION` | **只读**，绝不回写降级；`mutate()` 直接返回，界面也不假装改成功 |
| 记录读不懂 | 挪到 `db:salvage:<时间>` 留证，不拿种子盖掉 |
| 导入 / 回滚 | 一样走阶梯，不硬贴当前版本号 |

### 两个实测踩到的坑

**1. 迁移只按版本号跳过是不够的。**
只要版本号被盖上、对应的迁移却没跑过（发布顺序出错、热替换拿到半新半旧的
模块、有人手改过记录），那条迁移就**永远**不会再执行 —— 字段永久缺着，
毫无迹象。实测现象：记录标着 v15，`moreOrLessBp` 却是 `null`。

所以每条迁移**无条件跑一遍**。它们按约定本来就是幂等的
（一律写成 `if (x == null) x = 默认值`，不要写 `x = x + 1`），
几千行多跑两个 `if` 的代价，换"不可能漏"。

**2. 回写条件不能只看版本号。**
`if (from !== DB_VERSION)` 会漏掉"版本号已经新了、字段是自愈补上的"这种情况——
补的东西只留在内存里，下次打开又没了。改成 `up()` 返回「我确实改了东西」。

## 18. ⚠️ IndexedDB 打开时不要写版本号（第二次事故）

第 16 节记的是"写大了"：升 v2 被后台标签页挡住，老用户卡在装载页。
当时的修法是「回到 v1、新数据放进新库」。

**但那时已经有一批浏览器被上一版升到了 v2**，而 `open(name, 1)` 在 v2 的库上
直接抛 `VersionError`。这批人于是退化成**纯内存模式**：页面能开、能改，
刷新全没，而且一句提示都没有 —— 比卡在装载页更坏，至少那个看得见。

版本号写死多少都是错的：写小了炸在升过级的机器上，写大了要赌一次升级。

```js
indexedDB.open(name)          // 不带版本号 = 打开这台机器上现有的那一版
```

既不降级也不触发升级。只有真的缺 store 时，才以「现有版本 + 1」重开一次去补建。
副作用是好的：被上一版升到 v2 的浏览器，数据这下读回来了。

## 19. 演示账套与真实账套

两套数据各存各的键（`db` / `db:live`），随时来回切，谁也不覆盖谁。
演示账套沿用老键 —— 现存用户的数据都在上面，不搬家就不会搬丢。

**空账套里唯一不能空的东西是人。** 登录态是
`db.users.find(u => u.id === session.userId)`，真实账套要是一个用户都没有，
切过去的一瞬间当前登录的人就"不存在"了，直接被踢回登录页 —— 自己把自己锁在门外。
所以切换时把当前这个人连同凭据一起带过去，并提到 admin：新账套里只有他一个，
没人能替他审批、也没人能替他配主体，权限卡在中间就是死锁。

两个会串账的地方顺带修了：BroadcastChannel 频道名要带账套（否则演示标签页
会把 63 张假 PI 广播进真实账套并落盘）；`resetToSeed` 在真实账套里的原点是**空**，
不是演示数据。

## 20. 分批出运：CI/PL 必须按批开

一张 PI 分 4 批出运是常态。在 `ShipmentLine` 之前，`Shipment` 只有 `piId` 和
一个「第 4 批」的文字标签 —— **系统不知道第 4 批里装的是什么、多少件**。
于是给第 4 批开装箱单，打出来的是整张 PI 的 8 万件和总箱数：柜号对、数量错，
而那张纸是要拿去清关的。

- `buildDoc(db, pi, kind, shipmentId?)`：不传 = 整票（跟以前完全一样），
  传了 = CI/PL 按这一批的实际装载出。**PI 和合同永远整票** —— 它们是合同，
  不随出运拆分。
- 有批次却没登记装了什么时，不允许默默按整票出单，直接拦下来说明原因。
- 溢短装 `moreOrLessBp`（默认 ±5%）：判「这单出完了没有」不能用
  `已出 === 订单量`，生产和装柜凑不出整数，死磕相等的话每张单最后都挂着
  几十件的尾巴，永远显示"未出完"，跟单员就再也不看这个状态了。

## 21. 收款计划：事件没发生就没有到期日

付款方式原来是自由文本「30% T/T 定金，70% 见提单副本」。人读得懂，
系统读不懂 —— 账龄只能拿客户级 `termDays` 从提单日一刀切，
**定金那部分一定算错**：定金是签约就该付的，不是发货后 30 天。

`PaymentTerm` 拆成分期后，最重要的一条规则是：

> **触发事件没发生，就不要编造到期日。**

「见提单副本 30 天」在开船之前没有到期日可言。给它算一个会污染账龄分桶、
催收清单和现金流预测。所以 `dueOn` 是 `string | null`，账龄多一档
**「待触发」**，界面显示「待开船」而不是一个看起来很确定的假日期。
演示数据里这一档占应收总额的 60%。

放货闸口（`blocksRelease`）替掉了跟单表备注里手写的「待客户付尾款后电放」——
那句话系统不认识，人一交接就漏，而漏了就是货款两空。

## 22. 打印：Logo 与签章必须是 \<img\>

浏览器**默认不打印背景图**。用 `background-image` 放 Logo 和电子章，
屏幕上一切正常、打出来的 PDF 上什么都没有，而且没有任何报错 —— 套打最经典的坑。

- 章用 `mix-blend-mode: multiply` 压在签字线上，才像盖上去的；
  上传提示里要求透明底 PNG，白底方块贴上去一眼就是假的。
- PDF 文件名取 `document.title`，打印前换成 `CONTRACT_MT26X04118_客户名`、
  打印后还原（`afterprint` + 定时器兜底，个别浏览器不触发 afterprint，
  标题不能被永久改掉）。
- 演示账套的单据一律盖水印：一张看不出真假的演示商业发票流到客户或海关手里，
  比界面上任何一个 bug 都严重。
