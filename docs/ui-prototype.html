一、这次重构解决的四个具体问题

① 里程碑读不出「进度」

原来是四个孤立圆点，看得出哪几步有日期，看不出这票走到哪、离下一步还有几天。新方案把圆点连成一条有填充进度的航程线，当前节点带光晕，超期节点转珊瑚红，悬停出「计划 vs 实际」。

② 一屏塞了两排筛选

九个筛选器平铺占掉两行。新方案保留最高频的三个（搜索 / 动态 / 仅进行中），其余收进「更多筛选」，并把已生效的条件以可单独删除的胶囊回显——筛完之后永远知道自己在看什么。

③ 数字和文字混在一种字体里

柜号、PI 号、报关单号、金额都是要逐位核对的数据。全部改用等宽字体 + 等宽数字，列与列之间小数点自然对齐，抄柜号时不会把 0 看成 O。

④ 「快捷更新」占了一整条右栏

原来它常驻右侧约 300px，没勾选时是空的，却让里程碑那一列在 1600px 以下的屏幕上被挤出可视区。新方案改成勾选后从底部升起的操作条：表格永远满宽，操作条只在需要时出现。这条改动与截图不同，如果你更习惯右栏，我改回去也很快。

⑤ 异常不会自己冒出来

停滞、超期、利润率为负、退税未关联，原来都要靠人去翻。新方案统一成语义色（松绿=正常 / 琥珀=待办 / 珊瑚红=异常），行首 3px 色条，看板首屏有「今天要处理什么」清单。

二、色彩

主色只有一个（航线蓝），语义色三个，两者严格分离：蓝色永远表示「系统的强调」，绿 / 琥珀 / 红永远表示「业务的状态」。深浅两套主题都调过对比度，导航轨在两种主题下都是深色，作为品牌锚点。

三、字体与层级

中文正文走系统字体栈（PingFang / 鸿蒙 / 微软雅黑），不外链网络字体，内网和离线环境都不会掉字。代码型数据统一等宽。

五、交互约定

  • 就地编辑优先。动态、状态、里程碑日期都点一下就能改，不必进详情页——这是跟单员一天要做几十次的动作。
  • 批量是一等公民。勾选多行 → 右侧「快捷更新」面板亮起 → 一次写完动态 + 日期，常用短语一键填入。
  • 详情用抽屉不用跳页。看完就关，列表滚动位置和筛选条件都不丢。
  • 破坏性操作必有撤销。删除、批量覆盖后弹出带「撤销」的提示条，5 秒内可反悔。
  • 每个手势都有按钮替身。不依赖右键、长按、拖拽这类不可发现的操作。
  • 空态说人话。不写「暂无数据」，写「当前筛选下没有进行中的批次，试试关掉『仅进行中』」。

技术选型

目标：一条命令跑起来、单进程单端口、没有重型中间件、数据库能从 SQLite 平滑换到 MySQL

推荐方案：Next.js 15 全栈单服务 + Prisma + SQLite。前后端同一个工程、同一个进程、同一个端口，npm install && npm run build && npm start 就能用；数据库就是一个 .db 文件，拷走即备份。要上 MySQL 时改一行 provider 加一条连接串。

二、SQLite → MySQL 的切换路径

  • schema.prisma 里 provider 从 sqlite 改成 mysql，DATABASE_URL 换连接串，跑一次 prisma migrate，代码零改动。
  • 迁移目录按方言分开维护（prisma/migrations-sqlite / -mysql），因为两边生成的 DDL 不同。
  • schema 只用两库都支持的类型：不用 SQLite 特有写法，不用 MySQL 的 ENUM（状态一律存字符串 + 应用层枚举）。
  • 存量数据用一次性导出导入脚本搬过去（scripts/migrate-to-mysql.ts），本身也是备份工具。
金额一律用整数存。SQLite 没有真正的 DECIMAL，浮点会在核算和退税上凑不平账。约定：金额存「分」（BigInt），汇率存 6 位小数的整数（6.7392 → 6739200），只在展示层格式化。这条在第一行代码之前定下来，后面改成本极高。

三、部署

  • 裸机 / 群晖 SSH：npm ci && npm run build && npm start，默认 3000 端口，用 pm2 或 systemd 守护。
  • Docker（群晖套件推荐）：一个镜像 + 一个数据卷，docker compose up -d 完事。没有第二个容器。
  • 备份：SQLite 阶段就是定时拷贝那个 .db 文件；MySQL 阶段用 mysqldump。
  • 升级：拉代码 → build → 重启，迁移在启动时自动执行。

五、权限

两个维度组合，不做复杂的 RBAC 树：角色（管理员 / 业务员 / 跟单 / 采购 / 财务 / 只读）决定能进哪些模块和能不能改；数据范围（本人 / 本组 / 全部）决定看到哪些行。财务字段（成本、利润率、应付）对业务员默认隐藏，可按角色单独开。

七、需要你拍板的问题

1. 这套系统是替换现有的，还是并行重建？

如果是替换，我需要知道现有系统的数据能不能导出（Excel 就行），我按导出结构设计导入器；如果是并行，第一期就只做只读的展示层，不碰写入。

2. 第一期先落哪个模块？

我的建议是跟单表——它是使用频率最高、Excel 最难承载的一块，做完就能立刻见效。

3. 多公司段是怎么划的？

退税页有「晓行天下 / 供应链」两个段。这是两套独立账套（数据完全隔离），还是同一套数据的开票主体不同？这决定表结构要不要加租户维度。

4. 手机上要用吗？

如果业务员在外面要查跟单状态，我会把跟单表和订单做成移动端可用的卡片视图；如果只在电脑上用，我就把宽度全部让给数据密度。
